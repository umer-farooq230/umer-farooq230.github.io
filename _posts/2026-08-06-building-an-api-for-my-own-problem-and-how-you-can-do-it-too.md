My thinking shifted from straight solutions to complete systems and how a problem goes through many stages before becoming a whole end to end solution. So I wanted to take a real problem from start to finish.</p><p>From this article I hope to give you a blueprint how I think and tackle problems, hopefully you can add some steps into your way of thinking too</p><p><strong>Try My API for Free: </strong><a href="https://rapidapi.com/umerfarooq230/api/email-urgency-scoring-api/playground/apiendpoint_cd398009-c9b2-4f79-a9ec-5c99cf3e457f">Email Scoring API</a></p><h4>The Problem</h4><p>Many of my friends complained about their flooded inboxes with spam, useless subscriptions, events updates, older email lists, etc. And important emails vanishes between them, that’s a bigger problem for business owners as they have hundreds and thousands of emails monthly, and reading each one completely to determine its agenda is not practical</p><p>And that was the problem to solve systematically</p><h4>The Approach</h4><p>Like most side projects, this one did not start with a startup idea or a business plan. It started with a small problem that kept repeating itself. I wanted a simple way to decide which emails actually needed my attention.</p><p>At first I thought about building something just for myself. Before writing any code, I tried to understand the decision I was making every time I opened my inbox.</p><p>It looked something like this</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/830/1*Bp3xyQQtzlp-WmGqjobzpQ.jpeg" /><figcaption>Personal Miro Board</figcaption></figure><p>Around this time I also watched a Fireship video about APIs. That eventually led me to Code with Ania Kubów’s API tutorial. Those videos did not give me the solution, but they helped me understand how an API should expose functionality instead of focusing on the interface</p><h4>What Didn’t Work</h4><p>This step had two levels of execution. The first version was only for me. Hard coded values, trigger words, fixed scoring system and simple thresholds. If an email contained words like “refund” or “cancel”, it received extra points. Simple and clean</p><p>The problem appeared when I imagined someone else using it. My definition of an important email is probably different from a customer support team or an online store.</p><p>Second step was to make it adaptable to scale for different owners, businesses and thinking like an engineer. So no hard coded values or rules, just a simple question: “How can someone else define what matters to them?”. Answering this question will eventually solve the problem.</p><h4>The Pipeline</h4><p>Here’s what happens when an email hits the system — no black box, just a straight line from text in to a number out.</p><p><strong>1. The email comes in</strong><br> Just three plain things: subject, body, sender. That’s it. This shape is defined in schemas.py .One file that says &quot;an email looks like this, nothing more.&quot;</p><p><strong>2. It gets checked against a list of words</strong><br> A dictionary of phrases that usually mean trouble (“refund,” “chargeback,” “legal action”) and phrases that usually don’t (“thanks,” “just wondering”). Each word carries a weight. Lives in triggers.py, and the core function is about as plain as code gets:</p><pre>find_matches(text, triggers) → list of (word, weight) pairs found</pre><p><strong>3. The highest match wins, not the total</strong><br> My first instinct was to add everything up. Wrong move, five polite words shouldn’t outscore one real “chargeback.”</p><pre>base_score = highest weight among all matches</pre><ul><li>One bad word is enough to flag something serious</li><li>That’s how people actually read an inbox, you react to the worst part, not the average</li></ul><p>This lives in scoring.py, the heart of the system.</p><p><strong>4. A few small signals nudge the score</strong><br> Each one is its own tiny function does one job, nothing else:</p><ul><li>ALL CAPS subject → small bump</li><li>Multiple exclamation marks → small bump</li><li>Sender is marked VIP → bump</li><li>Thread’s been sitting unanswered for days → capped bump</li></ul><p>None of these decide anything alone. They just adjust a score the words already set.</p><p><strong>5. The number becomes a label</strong><br> 8+ is Critical. 5–7 is Needs Attention. Below that, Low Priority. This mapping sits in its own file, categories.py — so changing what counts as &quot;Critical&quot; means editing one small file, not touching the scoring logic.</p><p><strong>6. Every account gets its own rules</strong><br> A bakery and a logistics company don’t care about the same words. So before scoring anything, the system asks one question: “<em>what are this account’s rules?” </em>and scores against whatever comes back. Nothing is hardcoded per business.</p><p><strong>7. Everything gets written down</strong><br> Every score, every match, every timestamp, saved. Not for the sake of storing data, but so that six months from now, “why did this get flagged?” has an answer sitting right there. One file, storage.py, is the only part of the system allowed to touch the database. Everything else just asks it politely.</p><p><strong>8. No language model, anywhere in this loop</strong><br> That was the point from day one:</p><ul><li>No waiting on a response</li><li>No unpredictable cost per email</li><li>No guessing why a score came out the way it did</li></ul><p>Just words, weights, and a handful of small, honest files — each one doing exactly one job.</p><p>An email goes in one end. A number and a reason come out the other. Nothing in between is a mystery.</p><h4>Why an API</h4><p>At one point I considered building a web application or even a browser extension. Both would have solved my own problem. The issue was that they solved it in only one place.</p><p>An API felt like the better foundation. A web application can call it. A browser extension can call it. A CRM can call it. Even a small automation script can use the same endpoint.</p><h4>The V1</h4><p>The current version does what I originally wanted it to do. It accepts an email, evaluates it, and returns structured information that another application can use. It is containerized with Docker, documented, and simple enough to integrate into other projects.</p><p>There is still plenty to improve. I want users to define their own scoring rules without touching the code.
